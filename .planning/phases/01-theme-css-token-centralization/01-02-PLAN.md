<objective>
Lay the token foundation and the two shared primitives the migration depends on, with ZERO change to rendered output. Define the 7 locked semantic tokens (D-01) and wire the Tailwind v4 dark-mode variant mechanism (THEME-02), and create `Section.tsx` (D-02) and `Button.tsx` (D-04) so Plans 03/04 only have to consume them.

Purpose: Centralize the color system (THEME-01) and de-duplication primitives (THEME-03) in one place before any feature file changes, so migration becomes mechanical find/replace + import.
Output: Extended `app/app.css`, new `app/shared/Section.tsx`, new `app/shared/Button.tsx`.

IMPORTANT — surfaced planning decisions (read before implementing):
- Token VALUES are chosen to MINIMIZE visual delta, not to match the research example verbatim. In particular `--color-surface: var(--color-zinc-950)` (NOT gray-950) because 9 usages are zinc-950-based vs 1 gray-950, so this keeps the maximum number of pixels identical. This is within Claude's discretion (D-01 locks token NAMES/SET, not values).
- The locked 7-token set forces a bounded, sub-perceptual shade normalization: three muted greys (zinc-300/400/500) collapse to one `muted` token, two accent purples (purple-300/400) collapse toward `accent-hover`, and a decorative purple-700 blur maps to accent. The migration (Plans 03/04) maps each literal to its NEAREST-VALUE token so residual diffs stay sub-perceptual; the Playwright tolerance from Plan 01 absorbs them.
- SC2 nuance: Phase 1 establishes the `@custom-variant dark` DIRECTIVE and tokens at current values only. It does NOT add a `.dark { }` override block with alternate (light) values — that is Phase 2's job (per CONTEXT domain boundary + 01-PATTERNS). So toggling colors is not visibly demonstrable this phase; "mechanism wired" is proven by the directive compiling and `dark:` utilities generating CSS. (Flagged to orchestrator.)
</objective>
