## Phase Goal

**As a** portfolio visitor, **I want to** switch between dark and light themes from the header, **so that** the site displays in my preferred appearance and remembers my choice across visits.

<objective>
Deliver the complete, working dark/light theme toggle as one vertical slice: a Header sun/moon button that flips the theme, persists the choice to localStorage, defaults to the browser's `prefers-color-scheme` on first visit, and applies the correct theme before first paint (no flash). The "detect default -> allow override -> persist" logic ships as a reusable `usePersistedPreference` primitive (DARK-05) that Phase 3's language toggle will reuse unchanged.

This plan implements all five phase requirements (DARK-01..05). Plan 02 (Wave 2) adds the light-mode visual-regression baseline and human sign-off.

Purpose: Give users manual control over appearance without changing any content, copy, links, images, or structure.
Output: Inverted `app/app.css` token blocks, two new hooks under `app/hooks/`, a `ThemeToggle` component, a wired Header, and an SSR-safe blocking script in `app/root.tsx`.

## Documented decisions (traceable)

- **D-01 (locked, corrected direction):** D-01 states this phase "adds the `.dark {}` override block with light-mode values." RESEARCH.md Pitfall 1 (HIGH confidence) establishes this phrasing has the value-inversion direction backwards. The intent of D-01 is honored — a `.dark {}` block plus new light-mode values both come to exist in `app.css` — but the corrected direction is applied: NEW light-mode values go into the base `@theme` block (default), and TODAY'S already-signed-off dark values move verbatim into a new `.dark {}` block. `.dark` present on `<html>` means dark theme (standard convention matching the existing `@custom-variant dark`).
- **Accent-hover AA decision (adopts RESEARCH.md Pitfall 3 / Open Question #1, grounded in DARK-04):** `accent` (fill role) stays byte-identical across themes at `purple-500`, preserving "purple stays the primary accent" (DARK-04). `accent-hover` (text/hover role) becomes theme-aware: `purple-400` in dark (unchanged) / `purple-700` in light (new), because literal byte-for-byte parity fails WCAG AA (2.64:1) for `accent-hover`'s real usage as nav-hover text on a light surface, while `purple-700` on white passes at 6.98:1. This is recorded here explicitly rather than applied silently.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| localStorage -> client JS | `localStorage["theme"]` is user/extension/devtools-writable; its value is read by both the blocking script and `usePersistedPreference` |
| module constant -> `dangerouslySetInnerHTML` | The blocking script string is injected as raw HTML into `<head>` at SSR time |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | `localStorage["theme"]` read in `usePersistedPreference` + blocking script | medium | mitigate | Validate against the `["light","dark"]` allow-list before using the value to toggle a class or set `color-scheme`, in BOTH the hook (`validValues` check) and the inline script; any other value falls through to `matchMedia` detection |
| T-02-02 | Tampering / Elevation of Privilege | `dangerouslySetInnerHTML` blocking `<script>` in `app/root.tsx` | high | mitigate | Keep the script string 100% static at build time — zero interpolation of any runtime/user value (`THEME_STORAGE_KEY` is a compile-time constant). No DOM-XSS vector because nothing dynamic is embedded |
| T-02-SC | Tampering | npm dependency surface | low | accept | No new packages installed this phase; `lucide-react` already vetted in Phase 1 (RESEARCH.md Package Legitimacy Audit records the check). No install task, so no legitimacy checkpoint required |
</threat_model>
